# DOC-RUNBOOK — Operations runbook

**Owner:** SRE / DevOps Agent (operational), Documentation Manager Agent (custodial)
**Status:** ACTIVE (Phase 0 output)
**Audience:** on-call engineer.
**Source of truth:** every `CMP-DEPLOY-*`, `CMP-ORCH-*`, `CMP-SNAP-*`, `CMP-CP-*` spec in `SDD.md`; every workflow in `.github/workflows/`; `DOC-DEPLOY-DECISIONS.md`.

Every procedure here references the `CMP-*` component or workflow file that actually implements it. There are no fictional procedures. Where a procedure depends on something not yet implemented, the dependent component is named and the gap is flagged.

When this document conflicts with `PLAN.md` / `SDD.md` / the active workflow files, those win and this is corrected.

## 1. Purpose

This runbook is the on-call playbook for Scanipy v3.2. It covers the worker lifecycle, the scan lifecycle, failure recovery, key rotation, determinism / labeling incidents, attestation incidents, CI gate failure response, tenant operations, and observability — for the AWS-resolved substrate (`CLAUDE.md §8`, `DOC-DEPLOY-DECISIONS.md`).

It does **not** cover:
- Application-level business logic of individual detectors — that belongs in each `DOC-CMP-DET-*` per-component doc.
- The algorithm internals — see `DOC-ALGS.md`.
- The customer-facing API surface — see `DOC-API.md`.

## 2. Worker lifecycle (CMP-SNAP-05, CMP-ORCH-03)

The worker lifecycle has four phases: **build**, **publish**, **launch**, **execute**.

### 2.1 Build

| Step | Detail |
|---|---|
| Trigger | A tagged release `v[0-9]+.[0-9]+.[0-9]+` lands on `main`. |
| Workflow | `.github/workflows/deploy.yml`, job `build-images`. |
| Base image | Pinned via `FROM` digest in `workers/snapshot/Dockerfile` and `workers/detector/Dockerfile` (`CMP-DEPLOY-02`). |
| Bundled tooling | `joern`, `codeql`, `git` pinned by digest (`CMP-SNAP-05 AC-SNAP-05b`). |
| `env_digest` semantics | The ECR image digest IS the `env_digest` (`AC-SNAP-05b`, `CLAR-DEPLOY-13`). Any tool-version drift produces a different digest by construction. |

### 2.2 Publish

| Step | Detail |
|---|---|
| Registry | Amazon ECR (`CLAR-DEPLOY-13`). |
| Authentication | GitHub Actions OIDC → AWS IAM via `aws-actions/configure-aws-credentials@v4`; role ARN in `secrets.AWS_DEPLOY_ROLE_ARN` (`CLAR-DEPLOY-11`). |
| Signing | Sigstore Cosign keyless signing using GHA OIDC as the signing identity (`.github/workflows/deploy.yml`, step "Sign images with Cosign (keyless OIDC)"). |
| Attestation | SLSA-3 provenance attestation generated by GHA and stored as an ECR artifact (per `CLAR-DEPLOY-13`). |

### 2.3 Launch

| Step | Detail |
|---|---|
| Compute | ECS Fargate (`CLAR-DEPLOY-01`); private worker subnet (`CLAR-DEPLOY-09`). |
| Trigger | SQS message in the per-priority queue (`CLAR-DEPLOY-06`); the scheduler (`CMP-ORCH-02`) emits the messages. |
| Task definition | Pinned to a specific image digest (`AC-SNAP-05b`). Updating the task def is a deploy action; not in the hot path. |
| Secrets | Injected via the ECS `secrets` block from AWS Secrets Manager (`CLAR-DEPLOY-05`). No filesystem secrets. |
| IAM scoping | Worker task role is scoped per scan via session policies that restrict S3 to `orgs/{org_id}/*` and KMS to the tenant CMK (`CLAR-DEPLOY-16`). |

### 2.4 Execute

| Step | Detail |
|---|---|
| Snapshot worker | `CMP-SNAP-05` — loads the source at the requested commit, computes the CPG via Joern, runs `CW-DETECT` (`CMP-SNAP-03`), persists the five snapshot artifacts to S3 with deterministic keys (`CLAR-DEPLOY-02`), stamps `env_digest` (`AC-SNAP-01c`). |
| Analysis worker | `CMP-ORCH-03` — loads the CPG once, fans detector jobs, stamps `origin` per finding (DOC-PARTITION §4), reports back via HMAC-bearer callback to `POST /api/v1/jobs/{job_id}/status` (`AC-ORCH-01b`). |
| Argument allowlist | `CMP-SNAP-05 AC-SNAP-05a` — any flag not on the sanctioned list is rejected. |

### 2.5 Failure modes

| Failure | First-response procedure | Owner |
|---|---|---|
| **Image pull failure** | (1) Check the ECR repository policy admits the worker task role. (2) Confirm Cosign signature verification did not fail (look in the task event log). (3) If the image was deleted, redeploy from the last green tag. | SRE |
| **Task OOM** | (1) Inspect CloudWatch Logs for the OOMKilled event. (2) Identify the snapshot size (CPG node count is logged on entry). (3) If the snapshot is in the >2x-median tail, raise an incident; the scheduler may need a separate large-snapshot queue. | SRE |
| **Snapshot timeout** | (1) Look up the snapshot ID in the `snapshots` table and confirm `precondition-status`. (2) If `full-reparse` was the route, the timeout may be a `CW-DETECT` overreach — file a `CLAR-*` if the timeout rate exceeds the `CW-DETECT` combined routing-rate target of ≤15% (`AC-SNAP-03b`). | SRE + Security Analyst (INV-4) |
| **DLQ accumulation** | Procedure in §4.1. | SRE |
| **Callback HMAC failure** | (1) Confirm the worker's shared secret matches the control plane's. (2) If shared secret rotation is in progress, the worker must be drained before rotation completes. | SRE |

## 3. Scan lifecycle (CMP-ORCH-01..03)

A scan flows through the following stages. State persists in the `findings` and `snapshots` tables (`CMP-CP-03`); transitions are logged via OpenTelemetry (`CLAR-DEPLOY-07`).

```
client → POST /api/v1/scans
            (CMP-ORCH-01, AC-ORCH-01a)
              │
              ├── If snapshot for (codebase_id, commit_sha, env_digest) missing →
              │     enqueue snapshot job on SQS snapshot queue
              │     (CMP-ORCH-02 emits, CLAR-DEPLOY-06)
              │
              └── Once snapshot ready, fan one job per detector_id →
                    enqueue on SQS analysis queue
              │
              ▼
Snapshot worker (CMP-SNAP-05):
   1. clone source @ commit_sha to ephemeral disk
   2. build CPG (joern)
   3. CW-DETECT verdict → write precondition-status row (CMP-SNAP-01)
   4. persist artifacts to S3 with deterministic key (CLAR-DEPLOY-02)
   5. stamp env_digest from container image digest (AC-SNAP-01c)
   6. callback POST /api/v1/jobs/{job_id}/status (HMAC-bearer)
              │
              ▼
Analysis worker (CMP-ORCH-03):
   1. load CPG (cached via S3 key)
   2. resolve detector via CMP-DET-02 registry
   3. run IFDS (CMP-CORE-01) or oracle adapter (semgrep/cpg-query/external)
   4. stamp origin per finding (DOC-PARTITION §4)
   5. emit SARIF in canonical CPG order (CMP-FND-01)
   6. persist findings (CMP-FND-02), provenance (CMP-FND-03)
   7. callback POST /api/v1/jobs/{job_id}/status (HMAC-bearer)
              │
              ▼
Attestor (CMP-CP-05) [runs on every detector/engine/Env change, NOT per scan]:
   - Core pipeline: byte-identical SARIF across two independent runs
   - Oracle pipeline: digest-stability + reproduction rate
              │
              ▼
SARIF export to customer dashboard (CMP-CP-04) +
   signed provenance chain available via auditor export (CMP-FND-03)
```

### 3.1 HMAC-bearer worker callback path

Per `CMP-ORCH-01 AC-ORCH-01b`:

- The control plane signs an HMAC over `(job_id, body_hash, timestamp)` using the per-worker shared secret.
- The worker re-signs on response; mismatch → the control plane rejects the callback with `401`.
- Replay window is 5 minutes (timestamp delta); past that the message is rejected even with a valid HMAC.
- Worker shared secrets live in AWS Secrets Manager (`CLAR-DEPLOY-05`), rotated quarterly. See §5.

### 3.2 Idempotency

Per `CLAR-DEPLOY-06` (SQS at-least-once), the callback handler deduplicates on `(snapshot_id, detector_id)` for analysis callbacks and on `(snapshot_id)` for snapshot callbacks. A duplicate callback is acknowledged but produces no second persistence.

## 4. Failure recovery

### 4.1 DLQ inspection

| Step | Action |
|---|---|
| 1 | Open the affected DLQ in the SQS console (queue names: `scanipy-snap-dlq`, `scanipy-analysis-dlq-{priority}`). |
| 2 | Read the first failing message and identify the `snapshot_id` / `scan_id`. |
| 3 | Query `findings` and `snapshots` tables (`CMP-CP-03`) to confirm whether the work partially completed. |
| 4 | Inspect CloudWatch Logs (`CLAR-DEPLOY-07`) filtered by `snapshot_id` for the failure cause. |
| 5 | If the failure is transient (network blip, KMS throttle), redrive the DLQ → primary queue. |
| 6 | If the failure is structural (parse failure, invariant violation), file an incident and a `CLAR-*` if scope is unclear. |

### 4.2 Re-snapshot procedure

When needed (e.g., a `CW-DETECT` version bump invalidates a prior `closed-world` verdict):

1. Identify the affected `(codebase_id, commit_sha, env_digest)` set.
2. Mark the existing snapshot rows as superseded (do not delete — see §9.2 retention).
3. Submit a fresh snapshot job via the control plane.
4. The new snapshot stamps a new `env_digest` (because the worker image digest changed, by `AC-SNAP-05b`).
5. Findings emitted under the new snapshot are independent of the prior set; differential-oracle re-partition lineage is preserved per §6.

### 4.3 Re-attestation procedure

When needed (e.g., after a detector/engine/`Env` change that should have triggered the Attestor but did not, or after a determinism incident is resolved):

1. Identify the SHA range that needs re-attestation.
2. Trigger `.github/workflows/attestor.yml` via `workflow_dispatch`.
3. The core pipeline runs against `tests/corpora/canary/` (if the corpus exists — see the workflow's `corpus_check` gate).
4. If the core pipeline fails, follow §7.
5. On pass, the previous attestation record is superseded in `findings.attestation_id`.

## 5. Key rotation (CMP-CP-02, CLAR-DEPLOY-04)

### 5.1 KMS CMK annual rotation

| Aspect | Detail |
|---|---|
| Trigger | AWS KMS automatic rotation (annual). |
| Operator action | None during normal rotation; KMS handles the rotation transparently. |
| Impact on ciphertext | None — envelope encryption pattern means rotation generates a new key version without re-encrypting existing ciphertext (`CLAR-DEPLOY-04`). |
| Verification | After rotation, confirm new `KeyId` version appears in the CMK history and a probe decrypt against existing ciphertext succeeds. |

### 5.2 Per-tenant CMK rotation on customer request

| Step | Action |
|---|---|
| 1 | Identify the tenant CMK by `orgs.id`. |
| 2 | Trigger an out-of-band KMS rotation (KMS `rotate-key-on-demand` or per-tenant procedure). |
| 3 | Re-issue any cached data keys held in worker memory (drain workers if necessary). |
| 4 | Verify decrypt of an existing `scm_credentials` row succeeds (probe). |
| 5 | Log the rotation event for SOC2 audit trail. |

### 5.3 Signing-key rotation impact on provenance

Per `CLAR-DEPLOY-04`: the envelope-encryption pattern means a key rotation does **not** invalidate prior signatures. The signed provenance record carries the `KeyId` (and version) used at sign time; verification uses that version even after rotation. Prior signatures remain valid indefinitely.

### 5.4 Worker shared-secret rotation (HMAC)

| Step | Action |
|---|---|
| 1 | Plan a maintenance window. Workers must drain before rotation. |
| 2 | Push new shared secret to Secrets Manager. |
| 3 | Restart workers; they pick up the new secret at task launch. |
| 4 | Update the control plane's verification key. |
| 5 | Confirm no callback rejections in the post-rotation hour. |

## 6. Differential-oracle incident procedure (CMP-SNAP-04)

This procedure runs when the differential reflection oracle disagrees with `CW-DETECT` on a snapshot — i.e., the oracle says "not closed-world" where `CW-DETECT` said "closed-world". See DOC-PARTITION §5.

### 6.1 Detection

| Source | Detail |
|---|---|
| Trigger | `CMP-SNAP-04` async reflection scanner emits a disagreement event. |
| Alarm | CloudWatch alarm on the `Scanipy/v3.2/DifferentialOracleDisagreementCount` custom metric. |
| Provenance | Every disagreement is written to provenance per `AC-SNAP-04c`. |

### 6.2 Response

| Step | Action |
|---|---|
| 1 | **Raise a determinism incident.** Open an internal incident ticket. |
| 2 | **Re-partition affected findings.** For every finding emitted by the affected snapshot with `origin = deterministic-core`: flip to `oracle-passthrough` (`CMP-SNAP-04 AC-SNAP-04a`). |
| 3 | **Append provenance event.** A re-partition event record is appended to the signed provenance chain (`AC-SNAP-04c`). |
| 4 | **Notify affected customers.** Within the labeling-correction SLA per `CLAR-SLA-01`: **24h for high-impact incidents, 7d for routine**. Numeric SLA to be finalized at Stage A go-live. |
| 5 | **Update the honest-labeling ledger.** The re-partition rate is recorded; if the ledger shows the rate climbing, escalate `CW-DETECT` precision investigation. |
| 6 | **Confirm permanence.** Verify that the affected `origin` rows are now `oracle-passthrough` and not flickering back. Reverse transition is forbidden (DOC-PARTITION §5.3). |

### 6.3 What this procedure must never do

- It must **never** silently retry the snapshot under the same `CW-DETECT` version hoping for a different verdict. The verdict is deterministic per snapshot; a flicker would be a bug.
- It must **never** delete a finding. INV-3 forbids deletion; the re-partition only changes the `origin` field.

## 7. Attestation incident (CMP-CP-05)

Triggered by a hard CI fail on the core pipeline — a byte-difference between two independent runs of `F` under fixed `(S_version, env_digest, LLM_TRIAGE=off)`.

### 7.1 First-response triage

| Step | Action |
|---|---|
| 1 | **Reproduce locally** — pull the failing SHA and run the Attestor twice on the affected corpus subset. |
| 2 | **Compare `cpg_order_hash`** between the two runs. If they differ, the canonicalization budget exhausted in different ways on different runs → investigate the budget exhaustion. |
| 3 | **Inspect `fingerprint_class` distribution**. A spike in `weak` may indicate a refactor that exceeded the canonicalization budget; this is not necessarily a bug but does change the determinism story (see INV-5). |
| 4 | **Identify pseudo-source candidates** — any non-determinism source the implementation should not depend on (clock, env vars, random seeds, hashmap iteration order, file-system glob order, parallelism non-determinism). |
| 5 | **File `CLAR-*` if scope is unclear.** A new pseudo-source class is unspecified scope; do not invent a fix inline. |
| 6 | **Block deploy** — the deploy workflow (`.github/workflows/deploy.yml`, job `pre-deploy-checks`) refuses to promote any SHA whose Attestor check is not green. |

### 7.2 Roll-back criteria

| Symptom | Roll-back action |
|---|---|
| The Attestor was previously green on the predecessor SHA, and the current SHA introduces the diff. | Revert the offending PR; redeploy the predecessor. |
| The Attestor has been red across multiple SHAs and the canary corpus has changed. | The corpus may have introduced a non-deterministic input; pin the corpus to its prior `corpus.lock` version while investigating. |
| The `env_digest` changed in this deploy. | Confirm tool versions are pinned; if not, that is the root cause. Per `AC-SNAP-05b`, image digest IS `env_digest`, so a tool drift is a deploy-side regression. |

## 8. CI gate failure response (CMP-CI-01)

The four named gates (`CLAUDE.md §15`) are required status checks on `main`. Failure response per gate:

### 8.1 Gate 1 — DSL proofs (AC-DET-01a)

| Aspect | Detail |
|---|---|
| Workflow | `.github/workflows/ci.yml`, job `dsl-proofs`. |
| Failure cause | A combinator was added without a discharged distributivity proof obligation, or an existing proof regressed. |
| Owner | Spec author + Architect (`.claude/commands/architect.md`). |
| Action | Author the missing proof in `analysis/ifds/dsl/`; do not relax the gate. |

### 8.2 Gate 2 — Falsifier CW (AC-SNAP-03a)

| Aspect | Detail |
|---|---|
| Workflow | `.github/workflows/falsifier-cw.yml`. |
| Failure cause | `CW-DETECT` produced a false negative on the reflection corpus. INV-4 violation. |
| Owner | `CW-DETECT` owner (CMP-SNAP-03) + Security Analyst (`.claude/commands/security-analyst.md`, per RULE-9). |
| Action | A single FN is a **release blocker**. Add the missing reflection pattern to `CW-DETECT`; expand the corpus only after the fix lands; do not relax the gate. |

### 8.3 Gate 3 — Attestor (AC-CP-05a/c)

| Aspect | Detail |
|---|---|
| Workflow | `.github/workflows/attestor.yml`, job `attestor-core`. |
| Failure cause | Core pipeline byte-difference. |
| Owner | Incident response (§7); SRE owns the deploy-block side; Architect owns the root-cause investigation. |
| Action | **Block deploy.** Follow §7. |

### 8.4 Gate 4 — e-process martingale (AC-TRI-02b)

| Aspect | Detail |
|---|---|
| Workflow | `.github/workflows/ci.yml`, job `eprocess-unit`. |
| Failure cause | The e-process implementation no longer satisfies the martingale property `E[E_τ|H0] ≤ 1` across simulated stopping times. |
| Owner | CMP-TRI-02 owner + Security Analyst (per RULE-9, INV-3). |
| Action | **Blocks the customer-enablement deploy only**, not the baseline release. Triage the e-process implementation; do not enable triage / spec inference in production until the gate is green again. |

## 9. Tenant operations

### 9.1 Tenant onboarding

| Step | Action |
|---|---|
| 1 | A new tenant signs up via the dashboard (`CMP-CP-04`, SSO via Auth0 — `CLAR-DEPLOY-10`). |
| 2 | The control plane provisions an `orgs` row plus first-admin membership (`AC-CP-04a`). |
| 3 | The first user is auto-provisioned as `org-admin` per `CLAR-DEPLOY-12`. Subsequent users default to `org-viewer` pending admin promotion. |
| 4 | A per-tenant CMK is provisioned by `CMP-CP-02` (per `CLAR-DEPLOY-16`). |
| 5 | Per-tenant S3 prefix `orgs/{org_id}/` becomes operative. |
| 6 | RLS row-level security on `findings`, `snapshots`, `codebases` activates by `app.org_id` (`CLAR-DEPLOY-16`). |

### 9.2 Per-tenant data export

For retention-compliance, customer audit, or legal-hold requests:

| Step | Action |
|---|---|
| 1 | Identify the `orgs.id`. |
| 2 | Query the `findings` table with RLS bypass (admin role only) for all rows where `org_id = ?`. |
| 3 | Fetch the corresponding SARIF + signed provenance from S3 under the `orgs/{org_id}/` prefix. |
| 4 | Bundle: SARIF + provenance + e-process audit trail (if triage was enabled). |
| 5 | Deliver via signed S3 URL with bounded expiry. |
| 6 | Log the export event for SOC2 audit trail. |

### 9.3 Tenant offboarding

Per `CLAR-DEPLOY-15` (data retention):

| Artifact class | Retention | Action on offboarding |
|---|---|---|
| CPG tarball, reverse-symbol index, dynamic call graph, ΔG | 90 days | Lifecycle expiration applies; on offboarding the prefix is marked for accelerated deletion at the 90-day boundary. |
| Witness slice blobs | 1 year | Honored to retention. |
| SARIF + signed provenance | **7 years (S3 Object Lock — Compliance mode)** | **Cannot be deleted before the retention window**, per Object Lock. Offboarding does not bypass this; the tenant is informed at signing. |
| Findings table rows | Indefinite | Marked tenant-deactivated; rows preserved for audit. |

A legal hold on a codebase prevents deletion past the default retention; clear the hold before re-evaluating retention.

## 10. Observability (CLAR-DEPLOY-07)

OpenTelemetry SDK in workers and control plane. Exporters to AWS-native sinks.

### 10.1 CloudWatch Logs

| Aspect | Detail |
|---|---|
| Format | Structured JSON. |
| Filter dimensions | `org_id`, `scan_id`, `snapshot_id`, `trace_id`. |
| Log groups | `/scanipy/v3.2/control-plane`, `/scanipy/v3.2/snapshot-worker`, `/scanipy/v3.2/analysis-worker`. |
| Required fields | Every log line carries `S_version`, `env_digest`, `origin` where applicable (per `.claude/rules/02-provenance.md`). |
| Retention | 90 days default; 1 year for audit-tagged log groups. |

### 10.2 X-Ray traces

| Aspect | Detail |
|---|---|
| Trace boundaries | One trace per scan, spanning control plane → snapshot worker → analysis worker(s) → callback. |
| Service map | Visible in the X-Ray console; the canonical service map for a healthy production scan is a three-node chain (control plane, snapshot worker, analysis worker). |
| Span attributes | `S_version`, `env_digest`, `origin`, `determinism_partition`, `precondition-status` where applicable. |

### 10.3 Custom metrics

Under namespace `Scanipy/v3.2`:

| Metric | Owner | Use |
|---|---|---|
| `ScanLatencyP95Seconds` | CMP-ORCH-02 | Scheduler health (AC-ORCH-02a target: < 30 min p95). |
| `DifferentialOracleDisagreementCount` | CMP-SNAP-04 | Triggers §6 procedure. |
| `AttestorCoreByteDiffCount` | CMP-CP-05 | Should be zero; non-zero triggers §7. |
| `CWDetectCombinedRoutingRate` | CMP-SNAP-03 | Target ≤ 15% (AC-SNAP-03b). |
| `WeakFingerprintRate` | CMP-CORE-02 | Target < 5% (AC-CORE-02c). |
| `CanonicalizationBudgetExhaustionRate` | CMP-CORE-03 | Target < 1% (AC-CORE-03b). |
| `DLQDepthBySQS` | SQS (per queue) | DLQ alarm at depth ≥ 1. |

### 10.4 DLQ alarms

CloudWatch alarm on each DLQ at depth ≥ 1 → PagerDuty (CLAR-DEPLOY-07 notes PagerDuty as v3.2-baseline placeholder).
